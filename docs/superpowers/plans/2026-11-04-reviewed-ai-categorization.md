# Reviewed AI Categorization Implementation Plan — Stage 3B

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans, native inline TDD, task-by-task; one fresh-context whole-change reviewer at the end. Steps use checkbox (`- [ ]`) syntax. Do not dispatch implementer/reviewer pairs per task.

**Goal:** Persist bounded AI category suggestions for newly created eligible expenses and let the owner approve selected reviewed items without granting the model ledger authority.

**Architecture:** Five finance-owned tables hold user consent, server policy, creation jobs, usage reservations and proposals. A creation-only hook and a no-repeat-after-dispatch worker generate suggestions; single-item human commands reuse the private ledger writer and immutable receipts. The UI sequences a frozen selection of those commands rather than creating another batch/SQL mutation engine.

**Tech Stack:** Existing Python/FastAPI/Pydantic/async SQLAlchemy/PostgreSQL/Alembic, ARQ/Redis, bounded OpenAI Responses client, React/TypeScript/TanStack Query. No new dependencies, services or global client stores.

**Spec:** `docs/superpowers/specs/2026-11-04-reviewed-ai-categorization-design.md`, approved by user “tak” after design commit2dc69c4. ## Global Constraints

- Local implementation only: no real AI/OCR/provider activation, historical processing, production migration/deploy, main merge or push. Retain worktree/branch and unrelated Velo/Q7 files.
- PostgreSQL is truth; no JSON files as application state. LLM receives no ledger/SQL/tools, balances, account IDs, payment UUIDs, documents or amounts for calculation.
- Eligible source is a NEW ordinary `source=manual`, booked, positive PLN expense, one account posting and one exact technical-marker posting, rate1/source_amount==base_amount_pln; no Actual/mapping, loan, FX/refund, pending, allocation, manualstate or origin. Marker comes from explicit3A settings, not names/null/ancestors.
- Rule priority: only absent exact candidate or `rules_enabled=false` permits AI enrollment. A present but invalid/ambiguous/failed rule is not a fallback opportunity. AI enable is independent of rules enable. No scan of old transactions or terminal3A events, no backlog on enable.
- Server and user defaults OFF. Current user grant binds server epoch/config/privacy/cost scope; missing config or disabled server blocks opt-in. Disabling AI stops generation/publication, not local human approval of an already stored, still-valid proposal.
- The owner must still exist and be active at generation preparation, dispatch admission and publication. Identity deactivation/deletion revokes autonomous generation even if an old consent row remains; accounting retention is not permission to send.
- One provider call per job; only the process that proved a fresh committed `dispatching` transition may send it. No retry/refund after timeout, crash or ambiguous dispatch. Late usage may improve accounting, never revive publication.
- Configurable spec defaults: description500chars, taxonomy200categories, request32768bytes, maxoutput1024tokens, explanation500chars, five potential calls/user/UTCreservationday, TTL7days, predispatch job age24h, reviewpage20. Empty provider/model/key; no fallback to Advisor/Vision config. Storage bounds validated at startup.
- No truncation to fit taxonomy/description. Strict Structured Outputs with opaque category keys, decision existing/new/no_suggestion, confidence low/medium/high, bounded explanation and optional non-actionable newcategory. Confidence has no authorization path.
- Human approval requires owner/auth/CSRF, current immutable preview, version, explicit true and receipt key. It writes actual human manualstate plus `approved_llm` origin, not fake human confirmation by a worker. Rule writes still never create manualstate.
- v3 invalidates old interactive previews, but must not discard an otherwise valid persisted3A rule opportunity just because its complete source hash used v2. Read-only legacy rule compatibility is allowed only with absent state/origin and ALL current3A grants/guards; no rewrite, enrollment or replay of old ledger rows.
- Preserve payment count, accountPostingID/every mapped column, date/source/FX/amounts and document links; category postings remain sole monetary source, signed sum zero. No splits/new payment from a proposal.
- New categories: separate existing catalog create then existing manual assignment, two explicit human actions. No inline create-and-apply or automatic rule creation. New-category proposals cannot batchapply.
- SessionVersion fences all query keys, captured selection, pending writes and callbacks. Replayed receipts invalidate current reads; never install old snapshots as current truth.
- Follow owner-document→category-tree serialization; no late account locks or policy/rule FKs in creation enrollment. Server-policy setters lock only server-policy rows and never bulk-update jobs/ledger while holding that lock.
- No accurate PLN cost without configured versioned pricing/billing. Calls/reservations and known tokens are exact; missing usage is visibly unknown, not zero. Never release an admitted call slot on a guessed billing outcome.
- Only one additive migration generation/rehearsal in a new owned finanse_test schema; no backfill. Full test/lint/type/build/E2E and exact-source proof after whole-review. Do not rerun an unchanged full suite merely to repeat a completion claim.

## Review Focus

1. Late completion after revoke, expiry or lease recovery may record usage once, but must not produce a proposal or a second call (Task2 ticket/recovery test).
2. Disable/config rotation racing the actual network send must obey the documented dispatch-commit admission point, without holding DB locks over network or introducing global-policy/job lock inversion (Task2 barrier tests).
3. Existing3A early returns must not suppress AI when rules are OFF, and neither enable/startup nor a newly approved rule may enroll historical rows/events (Task1/2 creation tests).
4. AI approval creates manualstate, so subsequent same-category manual confirmation must still replace approved_llm origin; every history endpoint must display the truthful origin (Task3 no-op/projection regressions).
5. Batch cache refresh, auth refresh, uncertain responses and logout/login must not replace a frozen selection, change retry keys or approve unseen items (Task4 batch/session tests).

### Schema and interface decisions

Five Base tables:
1. `CategorizationSuggestionSettings`: uniqueuser, enabled=false, version>0, consent_at, accepted_server_epoch/fingerprint. Its version IS the user consent epoch (no duplicated epoch counter). No FK to mutable3A marker/settings/policy rows.
2. `CategorizationLlmPolicy`: singletonid1, enabled=false, epoch>0, configuration_fingerprint, changed_at. Read of absent row yields disabled/epoch0 without writes.
3. `CategorizationSuggestionJob`: unique(user_id,transaction_id) creation opportunity; opaque sourceUUID (no source/policy/rule/consent FK), source_context_sha256, marker/settings/user/server versions, configfingerprint; ready/preparing/reserved/dispatching/completed/cancelled/failed/uncertain; attempts, lease/deadline/next_attempt_at, packet_json/private_key_map/taxonomyhash/requesthash, result_kind(existing_category/new_category/no_suggestion|null) and safe reason. Packet persisted only after controlled preparation; no mirrored amount column.
4. `CategorizationLlmUsageReservation`: uniquejob FKRESTRICT, user/dateUTC, reservation_version, held_by_lease_token, state reserved/dispatching/known/unknown/released, dispatch_nonce, configfingerprint, nullable nonnegative provider input/outputtokens and response_id_hash. Index(user_id,usage_date,state); retained when source disappears. No daily-counter table.
5. `CategorizationProposalItem`: uniquejob FKRESTRICT, owner, transactionFK SETNULL, source/request/taxonomy hashes, immutable generated description/map/decision/explanation/confidence/newcategory JSON, nullable existingtargetFKRESTRICT, version/status/expiry/approvalreceiptFK. Existingtarget required only for existing_category; a newcategory has no target authority. Job/no_suggestion completes without an item; its safe outcome stays on the job.

Use explicit IS NOT NULL in conditional consent/active-grant checks, not nullable SQL comparisons that accidentally pass UNKNOWN. `reserved/dispatching/known/unknown` usage states retain a slot; released does not. Actual usage is nullable nonnegative integer metadata, never guessed zero or a currency amount. No source-delete cascade reaches jobs/reservations.

Add origin.proposal_item_id nullableFKRESTRICT; extend `ck_rule_origin_kind` with approved_llm. Add a new conditional check requiring proposal/receipt/hash and nullrule fields for approved_llm, and proposalnull for other kinds. Keep old approved_rule checks and `TransactionCategorizationState.source='manual'` unchanged. New metadata registration must work for app, Alembic and focused test collection.

`SuggestionConfig` is immutable with secret reprdisabled; `get_suggestion_config(settings) -> SuggestionConfig | None`. Dedicated `FINANCE_SUGGESTIONS_*` settings carry the spec defaults. Fingerprint provider/base/model, actual prompt+schema/privacy versions and limits; no secret in fingerprint/log/API. Reuse the existing OpenAI base-URL validation and client, no alternate host/fallback. Add implementation defaults timeout30s/lease90s/jobtimeout120s, predispatch attempts3, backoff10/60s, dispatchbatch20 and poll2000ms, all configurable; lease must exceed wall-time timeout plus a safety margin, and per-function jobtimeout must exceed lease.

- `suggestion_policy_snapshot(db, owner) -> SuggestionSettingsResponse`: stored userflag/version, effective_enabled, available, safe blockedreason, serverepoch/fingerprint, public limits/privacy text; no key/private model config.
- `change_suggestion_settings(db, owner, data: SuggestionSettingsChange, *, idempotency_key: str) -> SuggestionSettingsResponse`: expected_version, enabled StrictBool; enabling also expected_server_epoch/fingerprint and explicit `confirm_future_only=true`, `confirm_data_export=true`. Disable needs current userversion, not a still-current providergrant. Receipt/audit and version increment atomically; unavailable enable409, invalidbody422, owner scope.
- `set_suggestion_policy(db, *, enabled, expected_epoch, performed_by, config) -> PolicySnapshot`: INTERNAL ONLY, envkill-switch/configready required for enable. Reconcile drift fails closed/increments epoch. Never adopt the new fingerprint while leaving old grants effectively active; never scan ledger or bulk-pause jobs under this rowlock.
- `get_suggestion_usage(db, owner, usage_date: date) -> SuggestionUsageResponse`: UTC reservationday, limit, held/dispatched/known/unknown/released counts, known tokens, remaining_slots, `cost_status='unpriced'`; unknown is not zero.

- `reserve_suggestion_call(db, lease, packet) -> ReservationResult`: quota owner+UTCday advisory lock surrounds count(nonreleased) and uniquejob insert/CAS. Existing reserved slot is reused, released nosend slot can be re-reserved under a new version; known/unknown/dispatching never refunded/reused for another call. Usage day is the reservation-admission UTC day, not an invented provider billing date; crossing midnight does not duplicate a reservation.
  A full daily quota gives cancelled/quota_exceeded with no reservation/call and no next-day paid backlog. Input/catalog limits and maxage similarly end safely with a visible manual fallback. Only demonstrably transient nosend failures use bounded predispatch retries.
- Reservation operations first lock/verify the current job lease, then quota advisory, then reservation; no later owner/tree locks in that transaction. A new predispatch claimant reusing a held slot increments reservation_version and changes held_by_lease_token without charging another slot. `release_nosend_reservation(db, lease, reservation_id, expected_reservation_version, *, reason) -> bool` matches owner/current lease/heldtoken/version/state=reserved; a stale worker cannot release a successor's slot. Recovery may release a terminal nosend slot under the same job-first protocol. Nothing in dispatching/known/unknown is released.
- `admit_suggestion_dispatch(db, lease, reservation_version) -> DispatchTicket | None`: receipt/owner-document→tree→job→ledger/state/origin→userconsent→serverpolicy→quota→reservation protocol. Recheck actual env/config/grants/source/taxonomy/rule priority and CAS reserved→dispatching, assign one dispatch_nonce. Caller must COMMIT successfully and close transaction BEFORE invoking provider. Ambiguous/failed commit means NO send; recovery treats a possibly admitted ticket conservatively.
- `record_suggestion_usage(db, ticket, usage) -> None`: unique dispatch_nonce/version verifies immutable job/reservation identity, no owner/ledger locks. May change unknown→known once after lease/policy loss, never publish/re-reserve; identical duplicate noop, conflicting repeated usage safely rejected/audited.
- `finish_suggestion_job(db, ticket, outcome) -> SuggestionJobResult`: record actual usage first in its own idempotent short transaction. Publication in another transaction takes owner/tree→job→source/state/origin→consent/serverpolicy and validates unexpired lease + dispatchnonce + unchanged epochs/source/taxonomy. Create one immutable pending item for existing/newcategory, or complete no_suggestion withoutitem. Invalid/blocked output creates no actionable item; revoke/source change cancels publication, retains usage. Source deletion never removes accounting.
- `recover_suggestion_jobs(db, now) -> list[UUID]`: query only jobs; expired predispatch lease may retry within3attempts/backoff, expired dispatching becomes uncertain+unknown and never sends again. A late response cannot turn uncertain into completed/pendingitem.
- `process_suggestion_job(ctx, job_id: str) -> str`, `dispatch_suggestion_jobs(ctx) -> None`: ARQ wrapper/factory uses app sessions, no network under DB locks. After successful admission commit, exactly one provider invocation, then accounting/publication. Catch broker RedisError without attempt charge. Register via `arq.worker.func(process_suggestion_job, name='process_suggestion_job', timeout=settings.FINANCE_SUGGESTIONS_JOB_TIMEOUT_SECONDS, max_tries=1)` and cron20/50 seconds; domainDB, not ARQ automatic retries, owns recovery. Preserve existing document functions/global timeout. Installed func signature was verified read-only during planning.
